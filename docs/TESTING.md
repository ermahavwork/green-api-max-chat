# Проверка решения

Проверено 27 сентября 2026 года.

## Автоматические проверки

- `npm run build` — TypeScript strict и production-сборка Vite проходят.
- `npm test` — 42 проверки проходят: допустимый адрес API, телефон → chatId, валидация, статусы, дедупликация, очередь, ошибки сети и восстановление sessionStorage.
- `npm run test:e2e` — 4 браузерных сценария проходят в Chromium:
  1. Деморежим, безопасный вывод текста, локальный ответ, выход.
  2. Вход → телефон → канонический chatId → отправка → входящий ответ в том же чате → статус read → подтверждение очереди → перезагрузка → выход.
  3. Сетевая ошибка отправки: видимое предупреждение, сохранение черновика, отсутствие автоматических повторов.
  4. Мобильная навигация на 390×844, многострочный текст, сохранение черновика при переходах, отсутствие горизонтального скролла.
- `npm audit` — известных уязвимостей не обнаружено на момент проверки.

E2E-сценарии перехватывают запросы к GREEN-API через Playwright и возвращают ответы официального формата. Они не отправляют реальные сообщения.

## Проверка публичного сервиса

На `https://3100.api.green-api.com` выполнен OPTIONS-запрос без рабочих ключей для origin GitHub Pages: ответ 204, разрешены GET/POST/DELETE и Content-Type. Это подтверждает preflight на этом шарде, но не авторизацию или доставку сообщения.

## Что требует собственных данных

Живой обмен «браузер → MAX получателя → ответ в браузере» **не проверен**: тестовый авторизованный инстанс и согласованный получатель не предоставлены. Для такой проверки следуйте [SETUP.md](SETUP.md). Деморежим не является доказательством работы реальной доставки.

## Границы реализации

Только текстовые личные сообщения. Нет вложений, группового управления, вызовов, загрузки давней истории или серверного архива. Клиент не создаёт и не авторизует сам MAX-аккаунт: используется уже подключённый инстанс GREEN-API. Настройки внешнего инстанса не меняются автоматически.
